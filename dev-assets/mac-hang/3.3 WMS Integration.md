## Overview

The WMS integration defines how Salesforce Order Management (SOM) exchanges fulfillment instructions and execution events with Manhattan WMS.

In the future-state architecture:

* **SOM** is responsible for orchestration and fulfillment lifecycle
* **WMS** is responsible for physical execution (pick, pack, ship)
* **Middleware (Kafka-based)** provides decoupling, transformation, and event distribution

WMS remains the  **system of record for execution events** , while SOM consumes those events and determines downstream orchestration actions.

---

## Integration Architecture Pattern

### Core Pattern

The integration follows a  **hybrid event-driven + API interaction model** :

### Outbound (SOM → WMS)

* SOM publishes Fulfillment Order events
* Middleware consumes and delivers to WMS

### Inbound (WMS → SOM)

* WMS publishes events to Kafka
* Middleware transforms events
* SOM receives events via **Apex REST endpoints**

---

### Message Handling Model

* All inbound messages to SOM arrive as:
  * **JSON payloads via Apex REST**
* Middleware is responsible for:
  * Event consumption and routing
  * Payload transformation
  * Retry handling
  * Idempotency enforcement

---

### Guiding Principles

* Event-driven over synchronous integration
* Loose coupling between OMS and WMS
* WMS produces  **facts only** , not decisions
* SOM owns lifecycle and orchestration

When the WMS encounters a problem fulfilling a specific line item during pick or pack — short-pick, damaged unit, expired lot, wrong item scanned, etc. — it publishes this event to the OMS. The OMS then decides the downstream action (backorder the shortage, cancel the line, hold the order, notify the customer, etc.).

#### Design Principles

| Principle                         | Rationale                                                                              |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| **One event per line item** | Keeps payloads atomic; OMS can react per-line without parsing arrays of mixed outcomes |
| **Idempotent**              | `eventId`allows OMS to deduplicate retries                                           |
| **Reason taxonomy**         | Enumerated`reasonCode`enables automated routing; free-text`reasonDetail`for humans |
| **Quantity-aware**          | Reports both the requested qty and the actual qty picked so OMS can compute the delta  |

## 3.3.6 Document Generation and Processing

SOM will initiate document generation using a fire-and-forget integration pattern. After the appropriate fulfillment milestone is reached, SOM calls a Document Engine to instruct required fulfillment documents to be produced and routed for printing.

The Document Engine is expected to determine or coordinate where documents are printed, such as pack stations or another warehouse print location. The printed documents are then physically included in the shipment box as part of the packing process.

**TBD:** Final document generation and print-routing design is not yet defined. Current unknowns include Document Engine ownership, trigger timing, document types, print destination logic, error handling, reprint behavior.  SOM does not receive confirmation that documents were successfully printed.

| Document Engine          | Generate or coordinate required documents and instruct the appropriate print location. |
| Warehouse / Pack Station | Print, retrieve, and include documents in the shipment box during packing.             |

## 3.3.7 Specialized Fulfillment Flow

Specialized fulfillment covers fulfillment scenarios that diverge from the standard pick, pack, and ship flow. These scenarios may require operational intervention, alternate handling, or additional warehouse processing before the shipment can continue.

Examples include a QIC process where a box is removed from the line for quality inspection, an oversized item that must be moved to palletized fulfillment, or another exception-driven handling path that changes how the shipment is processed physically.

**TBD:** Final specialized fulfillment flow is not yet defined. Additional detail is needed from warehouse operations and integration teams to determine event names, ownership, status mapping, and whether SOM must pause, monitor, or only be notified of these flows.

### Example Specialized Fulfillment Scenarios

* **Quality Inspection / QIC:** Box is removed from the standard line for quality control review before shipment continues.
* **Oversized handling:** Item cannot follow the normal parcel flow and must be moved to palletized or alternate handling.
* **Manual intervention:** Shipment requires human review, repack, relabel, or warehouse exception resolution.
* **Alternate routing:** Shipment is routed to a non-standard station, lane, or fulfillment process.

### Expected SOM Considerations

* Determine whether the specialized flow is informational only or requires SOM lifecycle updates.
* Determine whether FO / FOLI status should be held, paused, or remain in progress.
* Determine whether customer visibility should change while the shipment is in specialized handling.
* Determine whether downstream notifications should be suppressed until the shipment returns to a standard flow.

### Open Questions

* What event identifies that a shipment has entered QIC or specialized handling?
* What event identifies that the shipment has returned to the standard flow?
* Does specialized handling occur before pack complete, after pack complete, or both?
* Is SOM expected to make any decision, or is this entirely warehouse-owned execution?
* What statuses and reason codes should be standardized?
